# Benchmark v62 - old against new, in one process

> **Superseded for capability reporting by [benchmark v63](../benchmark_v63/BENCHMARK_V63.md).**
> v62 remains the rule-repair record (did this change do what it claims?); v63 re-cuts the
> same evidence by landing/finding × radio and audits the claims above. An audit of this
> file's numbers is in [AUDIT_V63.md](../benchmark_v63/AUDIT_V63.md).

**Question.** For each situation this project cares about, what does the *previous*
rule do, what does the *repaired* rule do, and are the two measurements taken on the
same basis?

**Answer as of 2026-10-23:** 20 declared rows - 15 decided, 5 blocked. Three rows
separate the arms, one row fails in both, **no weight set is promotable**, and **not one
physical flight pair in the record is controlled**. The details are in
[RESULTS_V62.md](RESULTS_V62.md), regenerated by the runner; the version/weights report
is [REPORT_VERSIONS_V62.md](REPORT_VERSIONS_V62.md); this file is the declaration that
says what those rows mean.

## Why this file exists

Before v62 there was no old-against-new benchmark, only three things that get read as
if there were:

| what existed | what it actually measures |
|---|---|
| `benchmark_windows*.py`, `benchmark_worker.py` | render/physics **throughput** (frames per second, RAM/VRAM reserve). One configuration, no decision quality, 1-2 workers measured out of a requested 8-24. |
| [PILOT_MATRIX.md](../PILOT_MATRIX.md) | one row per **flight**, one configuration per row. It is a record of what happened, not a comparison; and every row is on a different source basis (see "What the flight tier found"). |
| [tools/compare_flights.py](../tools/compare_flights.py) | a **pairwise diff** of two recordings that refuses to interpret itself. Correct, but it answers "where did they part", never "did the repair work across the situation set". |

That is the gap this benchmark fills. It is not a replacement for flying; it is the
place where a claim about a repair has to be stated, paired and scored before a flight
is spent on it.

## Design

**Arms.** `baseline` and `repaired`, built by [arms_v62.py](arms_v62.py). Both arms are
the *same file*: the baseline is a subclass that overrides exactly the rule under test
with the pre-repair implementation, reproduced verbatim and commented with the episode
that exposed it. One process, one recogniser, one adapter, one mission layer, identical
inputs. This is deliberate: `E08_v61b` was compared against a v47 flight while flying an
unpromoted recogniser, and the comparison was read as if only the mission layer had
changed. A benchmark must make that mistake impossible, not merely note it.

**Tiers.**

* **decision** - scripted public observations into `protocol.step()`. Paired, exact,
  seconds. Six situations from the older E01-E08 batch plus three created by the repairs.
* **flight** - the recordings that already exist, compared field by field through their
  `source_receipt.json`. A pair is *controlled* only if every differing receipt field is
  one of the repairs under test and every field is hashed on both sides.
* **perception (weight ladder)** - every checkpoint that exists, on the same 1294 crops
  from three episodes, at both protocol gates. `run_weight_ladder_v62.py` rebuilds it;
  the tier reads `weight_ladder.json`.
* **mission** - the mission layer replayed over recorded long approaches, compared
  against what the flown mission layer decided.
* **tidewater** - declared Tidewater situations. Blocked on this host; see below.

**A row must be able to fail.** Every case declares its criteria before measurement,
and the suite is required to contain at least one row that fails in *both* arms - E02's
scale ambiguity. A benchmark where everything passes measures nothing; the self-test
([test_benchmark_v62.py](test_benchmark_v62.py)) enforces this, along with the baseline
reproducing each historical failure and no descent ever occurring on an unconfirmed
selection.

## What each tier proves, and what it does not

| tier | proves | does not prove |
|---|---|---|
| decision | the rule decides correctly on that evidence | that the aircraft flies differently, lands, or that the situation occurs in flight |
| flight | what two recorded flights did, and whether their bases are comparable | anything about a configuration that was never flown |
| perception | how a checkpoint scores on the exact crops that fooled a flight, with the sampler that actually flies | how it behaves on unseen scenes; nothing about the detector-only ranges (E08 25-40 s is blind for all three) |
| mission | what the mission layer would decide given the beliefs the actor actually held | that a different decision leads to a landing |
| tidewater | nothing yet - the rows are blocked | - |

## What the flight tier found

Every recording carries the hashes of what flew it. Across the 22 recordings in
`review_v60/` and `review_v61/` there are **3 different adapter versions, 5 different
protocol versions and 10 different harness versions**. Read together they show that the
current tree has flown **once**:

| group | adapter | protocol | harness | mission |
|---|---|---|---|---|
| E01_nominal_v60, E01_nominal_v60b | `a25de057` | `6979d929` | `e8a82445` / `f9b72b29` | not hashed |
| E01_nominal_v60c | `fd06a59b` | `08c20478` | `f9b72b29` | not hashed |
| E01_nominal_v60d, E01_v60..._r4, E02, E04-E08 | `fd06a59b` | `0be9b529` | `f9b72b29` / `9e721796` / `7b46ef41` | not hashed |
| E03_v60_forced / _rest / _repair / _ondeck | `505547e2` | `0be9b529` | four further harnesses | not hashed |
| **E08_v61c** | **`505547e2`** | **`7611b9a4`** | **`17fd154a`** | **`cd0b349c`** |
| current tree on disk | `505547e2` | `7611b9a4` | `17fd154a` | `cd0b349c` |

So:

* the actor adapter changed from `fd06a59b` to `505547e2` between the E04-E08 flights
  and the E03 repair, and the old adapter is no longer on disk - which is why
  `E08_v60` cannot be reproduced;
* every SILVER row in the pilot matrix was flown by protocol `0be9b529`, not by the
  protocol on disk (`7611b9a4`);
* `E08_v61c` is the only flight whose receipt matches the current tree.

Consequently **both flight pairs are `blocked_uncontrolled_basis`**: the repair is real
in the recording (`development_diagnostic_stop` -> `landed`, `collision_failure` ->
`landed`), but the same flight also carries a different adapter and, for E08, a mission
layer that was never hashed. The outcome difference cannot be attributed to the repair
from these two recordings alone. Attributing it is what the decision and mission tiers
do; confirming it needs a flight on one basis, which does not exist yet.

## What the Tidewater tier found

The three declared situations are the October reference flights (unpowered boat landed
37.1 s; 1.0 m/s with radio landed 43.3 s; low start 0.6 m/s without radio failed at
135.5 s). They are **blocked**, not passed:

* the October runs used the deployed R15 browser bundle through a staged runtime
  (`tidewater_runtime/`, asserted by `run_suite_v2.py`) on the Linux VM; that runtime is
  not present in this checkout;
* the MuJoCo and PX4 WASM modules and the headless probe are present locally, so the
  *world* could be run here;
* what is missing is the actor: there is no IPC bridge from Tidewater's observation
  schema to `IdentityExpertV60` plus the mission layer. Until that exists, a Tidewater
  row would measure the old policy, not the v60/v62 decision layer, and reporting it as
  an old-against-new row would be a fabrication.

A blocked row is cheaper than a wrong one. The prerequisites are recorded in the result
JSON (`prerequisites`, `blocked_reason`) so the tier can be turned on without redesigning
the suite.

## Running it

```bash
cd artifacts/teacher_repair_20261020/benchmark_v62
python run_weight_ladder_v62.py      # 3 checkpoints x 3 episodes, ~10 s on GPU
python run_benchmark_v62.py          # writes results.json and RESULTS_V62.md
python test_benchmark_v62.py         # 32 checks: the benchmark's own properties
```

All three are pure Python apart from the replay tier, which imports the frozen mission
package. Runtime is seconds to a minute; no flight, renderer or PX4 is involved.

## Adding a row

1. Name the situation and the recording that exposed it (`source`, `encodes`).
2. Write the criteria as behaviour, before running anything.
3. If the repaired rule is supposed to change the outcome, say so; if not, say that too
   - a row that cannot distinguish the arms is a regression guard, not a comparison, and
   is labelled `pass_both`.
4. A row that fails in both arms is a finding, not a mistake. Leave it failing and name
   the missing rule.
